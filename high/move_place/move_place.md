# 搬家

## 題目描述

給定一個 `n × m` 的地圖，每個格子可能放置一段不同形狀的水管，不同種類的水管具有固定的開口方向。

若兩個上下或左右相鄰的水管，彼此都朝向對方開口，則視為可以互相連通。連通關係具有傳遞性，因此可以形成不同的連通區域。

請找出所有連通區域中，包含水管數量最多的那一個，並輸出其大小。

### 水管種類

| 字元 | 開口方向    |
| -- | ------- |
| X  | 上、下、左、右 |
| H  | 左、右     |
| I  | 上、下     |
| F  | 右、下     |
| 7  | 左、下     |
| L  | 上、右     |
| J  | 上、左     |
| 0  | 無水管     |

## 輸入格式

第一行包含兩個整數 `n`、`m`，表示地圖的列數與行數。

接下來 `n` 行，每行包含 `m` 個字元，表示地圖中各位置的水管種類。

## 輸出格式

輸出一個整數，表示最大的連通區域所包含的水管數量。

# 水管連通區域

## 題目想法

曾經我編寫程式的能力還沒有那麼好的時候，我就看過這道題目，但當時直接被它嚇退了。不僅是因為它有各種奇形怪狀的水管圖案，也因為那時候雖然已經知道 DFS，卻不知道要怎麼把它套用到這一題上。

不過現在重新拿起這道題目，我幾乎一下子就寫出來了。我重新分析之後才發現，它其實就是一個非常基礎的求最大連通塊的 DFS 題目，只是利用各種不同形狀的水管，把題目包裝得看起來很困難而已。

一開始我還有想過要不要直接存每一種水管的圖案，不過後來發現根本沒有必要。我真正需要知道的資訊只有一件事情，就是它在上下左右四個方向中，哪些方向可以連通、哪些方向不能連通。所以最後我直接用四個 bool 來表示四個方向是否有開口，而不是去記錄每一種水管的形狀。我覺得用 bool 的邏輯會比用 0、1 更清楚，也比較不容易因為數值寫錯而造成 bug。

## 解題過程

我先建立一個三維陣列 grid。雖然是三維陣列，但最後一維的大小只有 4，分別代表右、下、左、上四個方向是否有開口，可以直接表示每一格水管有哪些方向可以連通。

接著再建立一個 visited，記錄哪些位置已經搜尋過，避免重複拜訪同一個位置。

另外建立兩個變數，ans 用來記錄目前最大的連通區域大小，而 total 則是在每一次 DFS 時，統計目前這一個連通塊總共有多少個水管。

開始 DFS 之後，我會先把目前的位置標記為已經走過，並更新 total。接著依序檢查四個方向，如果目前這個方向有開口，就先確認下一個位置沒有超出邊界，也還沒有拜訪過，再檢查下一格是否也剛好朝向目前的位置有開口。只有雙方都朝向彼此開口時，才代表兩格真的可以連通，這時才繼續往下一格進行 DFS。

最後在 main 中，對所有還沒有拜訪過的位置開始 DFS，每完成一個連通塊，就利用 total 更新 ans，最後輸出最大的連通區域大小即可。

## 解題方法思考

這一題真正困難的地方其實不是 DFS，而是題目利用很多不同形狀的水管來增加閱讀上的複雜度，很容易讓人一直把注意力放在水管圖案本身。

真正開始分析之後，我才發現完全不用去管它長什麼樣子，只要把每一種水管轉換成「四個方向哪些可以連通」即可。當所有水管都變成相同的表示方式之後，整個問題就變成非常標準的最大連通塊搜尋。

至於搜尋方式，我最後選擇使用 DFS。其實 BFS 也可以完成這一題，不過我覺得 DFS 的遞迴寫法比較直觀，整體程式也比較容易閱讀，一看就能知道目前正在往哪個方向搜尋，因此最後選擇使用 DFS。

## 複雜度分析

時間複雜度：

O(n × m)

每個格子最多只會被 DFS 拜訪一次，而每次最多檢查四個方向，因此整體時間複雜度為 O(n × m)。

空間複雜度：

O(n × m)

需要使用 grid 儲存每個位置四個方向是否有開口，以及 visited 紀錄是否拜訪過，因此空間複雜度為 O(n × m)。

## 學習心得

我覺得這題讓我很有感觸，因為以前的我看到這題時，光是看到那些水管圖案就覺得很可怕，甚至不知道要從哪裡開始思考。但現在重新做一次，我卻很快就發現它的本質只是求最大連通塊而已。

這也讓我更深刻體會到，很多題目真正困難的地方並不是演算法，而是它會利用很長的題目敘述或特殊的情境，把原本熟悉的問題包裝成另一種樣子。如果一直被表面的敘述影響，就很容易不知道該怎麼下手。

經過這題之後，我也更提醒自己，之後遇到新題目時，不要先被題目的背景或情境嚇到，而是要先思考它真正要解決的是哪一種類型的問題，只要找到它的本質，很多看起來很困難的題目，其實都會變得簡單許多。
