# 傳送點

## 題目敘述

有一排共 n 個格子，編號從 0 到 n-1。皮卡丘一開始在 0，目標是到達位置 P。

每次操作時，皮卡丘可以選擇：

向左移動 L 格

向右移動 R 格


移動完成後，如果所在位置為 i，會立即被傳送到指定位置 S(i)。但傳送只會發生一次，不會連續觸發，因此傳送後的位置才是下一次操作的起點。

若移動或傳送後的位置超出範圍 0 ~ n-1，則該次移動不可行。

起點與目標位置皆為停留點，也就是：

S(0) = 0

S(P) = P


請求出皮卡丘從 0 到 P 所需的最少操作次數；若無法到達，輸出 -1。

## 輸入格式

第一行包含四個整數 n, P, L, R，代表：

格子的數量

目標位置

每次向左移動的距離

每次向右移動的距離


第二行包含 n 個整數，第 i 個數字代表格子 i 的傳送位置 S(i)。

## 輸出格式

輸出皮卡丘到達位置 P 所需的最少操作次數。

若無法到達目標位置，輸出 -1。

# 傳送點

## 題目想法

一開始看到這一題的時候，我下意識想要直接使用 DFS 進行處理。因為題目中的移動方式是從一格跳到另外一格，看起來很像是在不斷探索不同路徑，因此第一個想到的是利用 DFS 搜尋所有可能走法。

但是仔細看過題目，並且實際操作幾次之後，我發現如果使用 DFS，除了需要額外維護目前的步數之外，也需要考慮不同路徑之間的比較，整體邏輯會變得比較複雜。而且如果沒有做好剪枝，時間複雜度也可能會有問題。

因為題目要求的是最少需要幾次操作才能到達目標位置，所以我想到這其實比較接近最短路徑問題，因此改使用 BFS 來處理。

不過在實際寫 BFS 的過程中，我發現這一題並不是完全標準的 BFS。因為題目有一些特殊條件，例如起點與終點一定是停留點，以及傳送只會發生一次，不會連續傳送，所以有一些一般 BFS 需要維護的資訊在這題其實可以省略。

因此我根據題目的條件，調整了原本 BFS 的寫法，讓它更符合這一題的狀態轉移方式。


## 解題過程

一開始我先建立 n、p、l、r 來儲存題目的基本資訊，並使用一維陣列 grid 儲存每個位置對應的傳送點。

接著建立 level 變數，用來記錄 BFS 目前搜尋的層數，也就是皮卡丘已經進行幾次操作。

進入 BFS 函式後，我建立 visited 紀錄哪些位置已經處理過，以及使用 queue 儲存目前可以到達的位置。

我先將起點 0 放入 queue 中。

進入 BFS 迴圈後，我利用目前 queue 的大小 sz 進行分層處理，讓每一輪代表一次操作後可以到達的位置。

取出 queue 前端的位置後，我先更新 visited，接著利用 grid 取得該位置的傳送結果。

因為題目規定傳送不會連續發生，所以傳送後的位置就是下一次可以進行移動的位置。

如果發現目前位置已經到達目標 P，就直接結束搜尋並回傳成功。

如果還沒有到達目標，就嘗試往左走 l 格以及往右走 r 格。

在判斷新的位置沒有超出範圍後，就將可以到達的位置加入 queue 中，等待下一層 BFS 處理。

最後在 main 函式中輸入 n、p、l、r 以及整張傳送地圖 grid，直接判斷 BFS 的結果。

如果成功找到目標位置，就輸出 level；如果 BFS 搜尋完仍然無法到達，就輸出 -1。


## 解題方法思考

這一題讓我了解到 BFS 不一定需要完全套用固定模板。

一開始我想到 DFS，是因為題目看起來像是在探索不同路徑，但是後來發現題目要求的是最少操作次數，所以 BFS 會更加適合。

在使用 BFS 時，我也發現如果完全照標準 BFS 寫法，可能會加入一些這題不需要的處理。因為題目的傳送規則有限制，而且起點與終點都是停留點，所以可以重新設計 BFS 中狀態代表的意義。

我最後將 queue 中的位置定義成下一次操作前皮卡丘所在的位置，取出時先處理傳送，再計算下一步可以移動的位置。

這樣可以避免把傳送也當成一個新的狀態，使整個 BFS 的邏輯更加簡單。

這題讓我學到，遇到演算法問題時，不一定只能套用已經學過的模板，而是可以根據題目的條件調整演算法，刪除不必要的部分，讓解法更符合問題本身。


## 複雜度分析

時間複雜度：

O(n)

原因：

每個位置最多會被 BFS 處理一次，而每次處理只需要檢查傳送位置以及左右兩種移動方式，因此整體時間與格子數量成正比。


空間複雜度：

O(n)

原因：

需要使用 grid 儲存 n 個位置的傳送資訊，另外需要 visited 記錄拜訪狀態，以及 queue 儲存 BFS 過程中的位置。


## 學習心得

這一題最大的收穫是讓我重新理解 BFS 的使用方式。

以前使用 BFS 時，通常都是直接套用固定模板，但這題讓我發現，真正重要的是理解 BFS 背後的概念，而不是只記住程式碼。

一開始看到題目時，我覺得它比較像 DFS 的探索問題，但在分析後發現最少步數才是重點，因此改成 BFS。

而在實作 BFS 的過程中，我也開始思考哪些資訊是真正需要維護的，哪些只是標準模板中的習慣寫法。

透過這題，我學會根據題目的限制修改原本熟悉的演算法，而不是每次都完全套用固定方法。這讓我在面對不同問題時，可以更靈活地設計解法。
