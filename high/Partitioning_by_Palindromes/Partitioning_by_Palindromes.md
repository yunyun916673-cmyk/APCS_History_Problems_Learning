# 最少迴文分割數量
## 題目意思
給定一個字串，請將這個字串切割成多個子字串，並確保每一個切出來的子字串都是「迴文」（亦即從左向右讀，和從右向左讀完全相同的字串）。請計算並找出最少可以將這個字串切割成幾個迴文子字串。
## 輸入格式
第一行包含一個正整數 N，代表共有 N 筆測試資料。
接下來的 N 行，每一行都會給定一個僅由小寫英文字母組成的字串。
## 輸出格式
對於每一筆測試資料，請輸出一行包含一個整數，代表該字串最少可以被分割成幾個迴文子字串。
## 範圍限制
 * 測試資料筆數 N 介於 1 到 20 之間。
 * 每個字串的長度介於 1 到 1000 之間。
 * 字串中所有的字元皆為小寫英文字母。


# 最少迴文分割數量
## 題目想法
一開始看到這題時，我使用了最直觀的方式：不斷進行字串切割。具體作法是透過字串相加，一個從前面加、一個從後面加，如果發現兩個組合出來的字串一模一樣，就記錄下來這是一個迴文。
但是，考量到題目字串長度最高會達到 1000，這種每次都要重新建構字串的作法一定會導致 TLE (Time Limit Exceeded)。因此，我意識到必須改變策略，後來決定改用動態規劃 (Dynamic Programming) 的方式來優化效能。
## 解題過程
為了解決重複判斷迴文的耗時問題，我建立了一個名為 temp 的二維陣列，用來記錄字串的左界與右界是否構成迴文。
初始化基本狀態：先把長度為 1 的子字串（左界與右界相同）都設為迴文。
處理長度為 2 的情況：為了讓後續判斷更方便，避免邊界溢出，我對長度為 2 的子字串也先進行了特殊判斷。
推導更長的字串：接著讓字串長度從 3 開始，一路往上進行判別。判別條件很簡單：只需看「左界字元與右界字元是否相同」，如果相同，就去查表看「中間夾住的那一段是否也是迴文」。
為什麼可以這樣做呢？因為我們是依照「長度」由小到大進行擴展判斷，所以當我們在檢查外層左右界時，中間的那一段狀態一定已經被算好並記錄下來了，絕對不會發生「還沒更新就拿來判斷」的情況。
## 解題方法思考
來到 main 函式後，核心邏輯就變得非常簡單，我把它想像成一個「拼拼圖」的模式。
我們透過一個一維陣列來記錄：如果要在某個位置之前「剛好填滿」這整段字串，最少需要拿多少塊「迴文拼圖」去拼它？
只要前面預先建表的步驟有確實做好，這裡我們只需要遍歷所有可能的切割點，不斷更新找出最少的拼圖數量（也就是最少分割次數）即可順利解出答案。
## 複雜度分析
### 時間複雜度：O(N^2)。建立二維的迴文狀態表需要雙層迴圈，時間為 O(N^2)；後續在計算最少切割次數時，同樣是一維 DP 搭配查找切割點，時間也是 O(N^2)。整體時間複雜度大幅下降，能輕鬆通過 N=1000 的考驗。
### 空間複雜度：O(N^2)。主要來自於儲存子字串迴文狀態的二維布林陣列 temp，以及一個長度為 N 的一維 dp 陣列。
## 學習心得
這題讓我深刻體會到「直觀的字串操作」與「動態規劃狀態記錄」在效能上的巨大差異。原本直觀暴力的 O(N^3) 解法雖然好想，但實戰中行不通。透過建表預處理迴文狀態，不僅解決了 TLE 的問題，也讓我練習到了如何透過「由小到大」的順序來建立狀態轉移。把分割問題具象化成「拼拼圖」，讓我在推導一維 DP 時思路變得清晰很多，是一次非常有收穫的解題經驗！
