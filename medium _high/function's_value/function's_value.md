# 函數運算式求值

## 題目敘述

題目給定三種函數：

f(x)：接受 1 個參數

g(x, y)：接受 2 個參數

h(x, y, z)：接受 3 個參數

接著輸入一個由這三種函數與整數組成的運算式。函數的參數也可能是另一個完整的函數運算式，因此需要依照函數的巢狀關係，將整個運算式求值，最後輸出結果。

## 輸入格式：
輸入一行，由函數名稱與整數組成。函數名稱會依照其參數數量讀取後續內容，整個輸入代表一個完整的函數運算式。

## 輸出格式：
輸出該函數運算式計算後的整數結果。

範例輸入 #1

f f f 2

範例輸出 #1

-5

範例輸入 #2

h f 5 g 3 4 3

範例輸出 #2

18

# 函數運算式求值

## 題目想法

一開始看到這個題目的時候，我曾經想過使用 STACK 的方式，配合每一個函式所需要的參數數量，先初始化為一、二、三，每遇到一個數值就減一。

但是後來實際思考之後，我發現這種方法會有一個問題。當時我最後寫出來的那一份程式，只能處理像是 H 套 G 套 F、H 套 F 或 G 套 F 這種函式參數數量遞減的情況。

如果變成 F 套 H 套 G、G 套 H、F 套 G、F 套 H 或 F 套 G 套 H，就沒有辦法正常處理。因為我原本的方法是利用每個函式剩餘的參數數量來判斷目前的狀態，這種方法只能在函式所需要的參數數量呈現遞減的情況下運作，否則就會發生錯誤。

後來我重新看了一遍這一題，也重新回頭思考我原本想到的 DFS。其實我一開始就有想到可以使用 DFS 的結構，只不過當時還不太會使用 stringstream。因為如果要使用 DFS，我需要先把輸入拆成一個個可以依序讀取的內容，所以當時我覺得需要 stringstream 才能實作。

不過那時候我沒有繼續深入了解 stringstream，而是先嘗試寫出其他方法。直到後來原本的方法卡住之後，我重新回頭撿起 DFS 和 stringstream，才發現這一題其實非常適合用 DFS 處理。

## 解題過程

我先把 f、g、h 三個函式分別實作出來，讓之後的 DFS 可以直接呼叫它們，也讓 DFS 本身只需要負責處理函式運算式的結構，讓每個部分的功能更加單一。

接著我使用 stringstream 將題目的輸入拆成一個個內容，並使用 line 儲存輸入中的每一個數值或函式名稱。

我再使用 pos 這個全域變數，記錄目前讀到 line 裡面的第幾個位置。

在 DFS 裡面，我會先讀取 line[pos]，再將 pos 往後移動。

如果目前讀到的是函式的標頭，就看這個函式需要多少個參數，再進行對應次數的 DFS。

例如遇到 f，就代表它需要一個參數，所以直接再做一次 DFS，將得到的結果放進 f 裡面。

遇到 g，就需要做兩次 DFS。

遇到 h，就需要做三次 DFS。

如果目前讀到的不是函式標頭，而是數值，那就直接將這個數值回傳。

這樣不管函式是怎麼互相巢狀的，都可以按照目前讀到的函式所需要的參數數量，繼續往下進行 DFS，而不需要限制函式之間的巢狀順序。

最後在主函式中，我只需要先初始化輸入資料，然後執行一次 DFS，就可以直接得到整個函式運算式的答案。

## 解題方法思考

一開始我想到的 STACK 方法，主要是依靠每個函式剩餘的參數數量來維護目前的狀態。但是這種方法會受到函式巢狀順序的限制，當函式的參數數量不是一直遞減時，就會變得很難處理。

重新思考之後，我發現這一題真正需要處理的其實不是參數數量的變化，而是函式之間的巢狀關係。

每一個函式都可以看成目前需要處理的一個節點，而它的參數又可能繼續包含其他函式，所以我只需要繼續往下一層處理即可。

因此這種函式套函式的巢狀結構，非常適合使用 DFS。

而且使用 DFS 之後，我不需要另外維護很多不同的變數或 STL，只需要利用 pos 記錄目前讀到的位置，再根據函式需要的參數數量決定要進行幾次 DFS，就可以把整個運算式處理完。

## 複雜度分析

### 時間複雜度：

O(N)

其中 N 是整個函式運算式中包含的 token 數量。每一個函式名稱或數值都只會被 DFS 處理一次，因此總時間複雜度為 O(N)。

### 空間複雜度：

O(N)

line 會儲存整個輸入的所有 token，而最壞情況下 DFS 的遞迴深度也可能達到 O(N)，因此空間複雜度為 O(N)。

## 學習心得

這一題讓我明白，很多時候，這種巢狀結構不一定是圖，也不一定是傳統的結構化題型。

像這種按照順序處理、但是內容又具有巢狀關係的題目，其實也能夠直接使用 DFS 進行處理，而且有時候會非常契合。

以前看到 DFS，我比較容易直接聯想到圖、迷宮或是需要走訪節點的問題。但這一題讓我發現，DFS 的核心其實不一定要建立在圖上，只要問題本身具有一層一層往下處理的結構，就有可能使用 DFS。

另外，這一題也讓我重新認識了 stringstream。原本我已經想到 DFS，只是因為當時還不熟悉 stringstream，所以沒有把這個想法實際做出來。後來重新回頭處理之後，才發現只要先把輸入拆開，原本的 DFS 想法就可以很自然地實現。

我覺得這也是我這一題比較重要的收穫：有時候真正卡住我的不一定是演算法本身，而可能只是某一個還不熟悉的工具。如果已經有一個合理的解法方向，就不應該太快放棄，而是可以回頭把卡住自己的那個工具補起來，再重新嘗試原本的想法。
