# 幸運數字

## 題目敘述

有 N 個人，每個人都有一個彼此不同的數字。

對任意一段連續區間 [L, R]，定義其中的「幸運數字」：

如果區間只剩一個數字，該數字就是幸運數字。

否則，先找到區間中最小的數字，並以它的位置為界，將區間分成左半部與右半部。

分別計算左右兩部分的數字總和，選擇總和較大的那一側繼續處理。

如果左右兩側總和相同，選擇右側。

若其中一側沒有任何數字，該側的總和視為 0。


持續進行上述操作，直到區間只剩一個數字。

請找出整個序列中最後得到的幸運數字。

## 輸入格式

第一行輸入一個正整數 N。

第二行輸入 N 個互不相同的正整數 A1, A2, ..., AN。

其中：

1 ≤ N ≤ 3 × 10^5

1 ≤ Ai ≤ 10^7

## 輸出格式

輸出最後找到的幸運數字。

範例輸入 #1

5

4 2 3 1 5

範例輸出 #1

4

範例輸入 #2

8

3 9 4 5 1 6 2 8

範例輸出 #2

9

# 幸運數字

## 題目想法

一開始我看到這份題目的時候，嘗試了各種方法，但最後發現都會 TLE。後來去查資料才知道，原來有一種演算法叫做 SGT（Segment Tree），還有另外一種演算法叫做 ST（Sparse Table），都可以非常方便地處理這種區間查詢的問題，把查詢的時間複雜度大幅降低。

這一題我最後留下了四份程式碼。

第一份程式是使用 SGT 搭配 DFS 進行處理，不過我後來發現，這樣的遞迴深度可能會出問題。所以我就去學習如何使用 Stack DFS，也就是第二份程式碼，把原本的遞迴改成自己使用 stack 來模擬。

後來我又發現，這一題其實可以看成一種尾端遞迴。因為每一次找到最小值之後，只會選擇左邊或右邊其中一側繼續，而且不需要回到原本的位置，也不需要再回頭處理另一個方向，所以整個過程其實只會形成一條路徑。

因此第三份程式碼我就直接把 Stack DFS 改成 while 迴圈，讓整個模擬過程變得更加簡單。

第四份程式碼則是我在學習完 ST 之後的成果。這一次我把原本 SGT 的區間最小值查詢改成使用 Sparse Table，讓查詢區間最小值可以在 O(1) 的時間內完成。

這一題也讓我實際接觸到了 SGT、ST、Stack DFS 以及 while 這幾種不同的處理方式，所以我把這幾份程式碼都保留下來，記錄自己從最初的想法，到後來學習新的演算法並修改解法的過程。

## 解題過程

在第三份程式碼，也就是 SGT 搭配 DFS 的版本裡面，我在建立完 N 之後，建立了四個主要的 STL。

LINE 用來記錄整個序列上的每一個值。

PT 用來記錄前綴和，讓我之後可以快速計算目前區間左右兩側的總和。

SGT 用來建立 Segment Tree，處理區間最小值查詢。

TEMP 用來儲存每個數字所對應的位置。因為題目保證所有數字都互不相同，所以找到最小值之後，就可以利用 TEMP 找到它原本在序列上的位置。

接著在 BUILD 裡面，我使用遞迴建立 SGT。

如果左界和右界相同，代表現在已經到達葉節點，所以直接把目前的值存進 SGT，並回傳給上方的節點。

如果還沒有到達葉節點，就把目前的區間從中間切開，再繼續往下遞迴。等左右兩邊都回傳之後，取兩邊的最小值，存進目前的節點，再繼續往上回傳。

因為我建立的 SGT 是用來處理每個區間的最小值，所以每一個節點儲存的就是該區間中的最小值。

接下來是 QUERY。

QUERY 的目標是找到指定區間中的最小值。

如果目前的區間完全在查詢範圍之外，代表它和我要找的區間完全沒有重疊，所以直接回傳無限大。這樣之後和其他區間取 min 的時候，就不會影響真正的答案。

如果目前的區間完全被包含在我要查詢的區間裡面，那麼就代表這整個區間都需要被查詢，因此沒有必要再繼續往下切，可以直接回傳目前 SGT 節點所儲存的最小值。

只有當目前區間和查詢區間有部分重疊，但是又沒有完全包含的時候，我才會繼續把區間二分，分別查詢左右兩邊，最後再取兩邊回傳值的最小值。

最後得到的就是指定區間中的最小值。

在 SIMUL 裡面，我先指定目前要處理的區間是 LEFT 到 RIGHT。

接著進入 WHILE 迴圈，只要 LEFT 小於 RIGHT，就代表目前還有至少兩個數字。

這時候先利用 SGT 找到目前區間中的最小值，再透過 TEMP 找到這個最小值在原本序列上的位置。

找到位置之後，就利用 PT 的前綴和快速計算最小值左邊與右邊的總和。

如果左邊的總和比較大，就把目前的區間縮小到左邊。

否則就縮小到右邊。

題目要求如果兩邊總和相同，要選擇右邊，所以我直接把相等的情況放在 ELSE 裡面處理。

不斷重複這個過程，直到 LEFT 和 RIGHT 相同。

這時候代表最後只剩下一個數字，而這個數字就是題目要求的幸運數字。

在 MAIN 裡面，完成初始化、讀入資料、建立前綴和以及建立 SGT 之後，直接輸出 SIMUL 的結果即可。

第二份程式碼則是我嘗試把原本的遞迴 DFS 改成 Stack DFS。

原本 DFS 是找到下一個要走的區間之後，直接呼叫下一次 DFS；而 Stack DFS 則是把下一個要處理的區間放進 stack，再從 stack 裡取出來繼續處理。

這樣可以避免遞迴深度過深造成的問題，也讓我實際練習了如何使用 stack 模擬遞迴。

不過後來我發現，這一題其實不太需要 Stack DFS。

因為每一次選擇之後，只會繼續走其中一邊，不會同時留下另一邊等待處理，所以 stack 裡其實不會真的累積很多個待處理狀態。

因此第三份程式碼就直接改成 WHILE。

我只需要記錄目前的 LEFT 和 RIGHT，每次找到下一個要走的區間後直接修改 LEFT 或 RIGHT，然後進入下一次迴圈即可。

這樣就可以把原本的 DFS 過程變成單純的一條路徑。

第四份程式碼則是我學習 ST，也就是 Sparse Table 之後重新實作的版本。

這一次 LINE、PT、TEMP 的用途基本上沒有改變，主要改變的是原本的 SGT 被換成 ST。

在 BUILD 裡面，我先把第一層，也就是 ST 的第 0 層，初始化成原本 LINE 中的每一個值。

這裡我的理解是，ST 的第一維代表區間長度是 2 的 i 次方，而第二維代表這個區間從哪一個位置開始。

例如 ST[i][j] 就代表從 j 開始，長度為 2 的 i 次方的區間中，最小的值。

接著我利用兩層迴圈建立整張 Sparse Table。

當目前要建立長度為 2 的 i 次方的區間時，可以把它切成左右兩個長度為 2 的 i-1 次方的區間。

因此我只需要取得左半部和右半部各自的最小值，再取兩者的 min，就可以得到目前整個區間的最小值。

在 QUERY 裡面，我先指定我要查詢的區間是 L 到 R。

接著找到這個區間中最大的 2 的 OVE 次方，也就是一個不超過目前區間長度的最大二次冪長度。

然後我從左邊取一段這個長度的區間，再從右邊往左取一段相同長度的區間，分別查詢這兩段在 ST 中儲存的最小值，最後取 min。

這兩段區間可能會互相重疊，但這並不會影響答案。

因為 min 具有冪等性，同一個數字就算被計算兩次，最後取 min 的結果仍然不會改變。

因此就可以在 O(1) 的時間內完成一次區間最小值查詢。

最後主函式的處理方式和 SGT 版本基本上相同，先完成初始化與 ST 建表，再不斷找出目前區間的最小值位置，比較左右兩側總和，決定下一個要處理的區間，最後輸出剩下的幸運數字。

## 解題方法思考

這題讓我最大的收穫，是我第一次比較完整地接觸到區間查詢的資料結構。

一開始我只知道直接模擬題目的操作，但當資料量變大之後，就發現如果每次都重新尋找區間最小值，時間複雜度會太高。

後來查資料之後，我才知道可以使用 SGT，也就是 Segment Tree，來處理區間最小值查詢。

學會 SGT 之後，我又進一步學到了 ST，也就是 Sparse Table。

我發現這兩個演算法雖然都可以處理區間查詢，但適合的情況不太一樣。

如果資料固定不會改變，而且我要查詢的東西具有冪等性，例如最大值或最小值，那麼 ST 可以讓查詢非常快速。

但如果資料會不斷變動，或者需要進行 UPDATE，那麼 SGT 就會更加方便，因為它可以在修改資料之後重新維護區間資訊。

另外，這題也讓我第一次實際嘗試 Stack DFS。

原本我只比較熟悉遞迴 DFS，所以看到需要把遞迴改掉時，我就想嘗試看看能不能用 stack 自己模擬。

實際做完之後，我才發現並不是所有遞迴都需要使用 Stack DFS。

這題雖然可以使用 Stack DFS，但因為每一次都只會往一個方向走，所以其實只需要 while 就可以完成。

這讓我開始注意到，在選擇演算法或資料結構的時候，不只是要想「能不能用」，還要想「這個問題真的需要它嗎」。

## 複雜度分析

SGT 版本：

### 時間複雜度：

O(N log N)

建立 SGT 需要 O(N)，之後每次查詢區間最小值需要 O(log N)，最壞情況下會進行 O(N) 次查詢，因此整體為 O(N log N)。

### 空間複雜度：

O(N)

主要來自 LINE、PT、TEMP 以及 SGT。

ST 版本：

### 時間複雜度：

O(N log N)

建立 Sparse Table 需要 O(N log N)，之後每次區間最小值查詢只需要 O(1)，而最壞情況會進行 O(N) 次查詢，因此整體仍然是 O(N log N)。

### 空間複雜度：

O(N log N)

主要來自 Sparse Table。

Stack DFS 與 WHILE 版本的主要差別在於處理目前區間的方式，而不是區間最小值查詢本身，因此在使用相同 SGT 的情況下，主要時間複雜度仍然是 O(N log N)。

## 學習心得

藉由這一題，我學到了線段樹 SGT 和 Sparse Table ST 這兩個演算法，也實際練習了 Stack DFS 和把遞迴改成 WHILE。

以前看到區間問題的時候，我比較容易直接想到暴力處理，但這次我開始知道，如果題目一直要求我查詢某個區間的狀態，就可以開始思考是不是有適合的資料結構可以幫忙。

尤其是 SGT 和 ST，我發現它們在很多區間問題中都非常好用。

後來我又進一步學習了 SGT 的 UPDATE，讓我更加理解這兩種方法之間的差異。

如果資料固定不動，而且我要處理的是像最大值、最小值這種具有冪等性的資訊，那麼 ST 可以非常方便地處理大量查詢。

但如果資料會變動，或者查詢的資訊不一定具有冪等性，那麼 SGT 就能夠提供更有彈性的處理方式。

這一題另外讓我學到的是，不要因為一個方法可以使用，就認為它一定是最適合的。

我原本為了避免遞迴深度問題去學 Stack DFS，後來卻發現這題連 stack 都不需要，直接使用 while 就可以。

所以這次的過程讓我不只是學會 SGT 和 ST，也開始學著分析一個問題真正需要什麼，而不是看到學過的工具就直接套上去。
