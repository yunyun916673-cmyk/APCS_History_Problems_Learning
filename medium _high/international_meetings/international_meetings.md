# 國際會議
## 題目意思
有 N 個國家準備進行雙邊會談，總共需要進行 N(N-1)/2 場會談。
請判斷是否能安排出一個時程表滿足以下所有條件。如果可以，請計算出最少需要的天數；若無法達成（例如順序矛盾導致死結），則輸出 -1。

每個國家每天最多只能參與一場雙邊會談。

每個國家 i (1 <= i <= N) 必須嚴格依照給定的名單順序與其他國家進行會談，順序為 A[i, 1], A[i, 2], ..., A[i, N-1]。

輸入格式
第一行為一個整數 N。
接下來有 N 行，第 i 行包含 N-1 個整數，依序代表國家 i 預定會談的對象編號 A[i, 1], A[i, 2], ..., A[i, N-1]。

## 輸出格式
如果可以安排出滿足所有條件的時程表，請輸出最少需要的天數。如果不可能達成，請輸出 -1。

## 範圍限制
3 <= N <= 1000

1 <= A[i, j] <= N

A[i, j] 不等於 i

數列 A[i, 1], A[i, 2], ..., A[i, N-1] 中的數字皆不重複。

# 國際會議
## 題目想法
這題其實不需要用到太過複雜的演算法，但因為題目本身需要維護與檢驗的規則很多（例如順序限制、一天一場限制等），所以整體而言的邏輯會變得較為複雜。核心重點在於釐清配對的先後順序，以及確保系統不會發生排程上的死結（Deadlock）。
## 解題過程
 * 資料結構定義：
   * ship[i][j]：儲存第 i 個國家第 j 場要和誰開會。
   * noww[i]：紀錄第 i 個國家接下來下一個要開第幾次會（進度指標）。
   * is_sleep[i]：記錄這個時間點該國家是否已經開過會議了（休眠/待機狀態）。如果已經開過就不能再開。
   * temp (Queue)：裡面存放 (A, B)，代表準備進行會議的國家組合。
   * level：記錄目前使用了多少時間點（天數）。
   * good：記錄目前已經完成了多少場會議。
 * 模擬流程推進：
   以類似 BFS 的層序走訪方式順著題目的結構進行模擬。在每一層（每一天）中，將 temp 中的組合拿出來檢查。
 * 配對條件檢查：
   必須滿足「A 下一個要進行會議的對象是 B，且 B 下一個要進行會議的對象也是 A」，這樣子才會繼續進行，否則就直接跳過該次配對。
 * 單日次數限制與延遲處理：
   如果雙方有任何一個國家正在待機（也就是這個時間點已經開過一次會了），該次會議也必須跳過。但是不能直接丟棄這個配對，必須把它重新放進 temp 裡面，因為雙方已經確認過可以進行會議了，只是剛好遇到有人在休眠，需要留到下一個時間點處理。
 * 狀態更新：
   確認配對成功後，直接更新雙方的 noww 以及 good，然後把它們都設為休眠模式（待機狀態）。接著檢查他們如果還有下一場會議的話，就繼續把新目標放進 temp 中。每一天（level）結束時，重置所有人的休眠狀態。
 * 結果判定：
   迴圈結束後，看是否開完所有的會議（good == N*(N-1)/2）。如果有的話就輸出總共花費的時間 level，如果沒有的話代表卡死了，直接輸出 -1。
## 解題方法思考
這題利用佇列（Queue）配合層級（Level）推進的方式來模擬「時間點」非常適合。雖然初步構想時可能會聯想到 DFS，但在實作上利用 BFS 的層次走訪思維，能更直觀地解決「每天每個國家只能比一場」的平行時間限制。利用 noww 陣列去追蹤每個國家的進度，巧妙地將複雜的先後順序問題轉化為單純的「目標核對」，是解這題的關鍵突破口。
## 複雜度分析
### 時間複雜度： O(N^2)
   總共需要進行 N(N-1)/2 場會議。佇列中每場會議最多只會被成功推進一次，即使因為 is_sleep 延後處理，攤提下來每個配對的檢查與重推次數仍在合理常數範圍內，整體時間複雜度與總會議數成正比。
### 空間複雜度： O(N^2)
   主要花費在建立大小為 (N+1) * N 的二維陣列 ship 上，以 N 最大為 1000 來說，記憶體使用量完全符合題目的 1024 MiB 限制。
## 學習心得
在實作這類充滿細節的模擬題時，邏輯的嚴謹度非常重要。例如必須確實檢查「雙方當前的目標是否互為對方」，以及在配對成功後不能忘記「將狀態標記為已休眠」，這些小細節都會直接影響答案的正確性或是造成執行錯誤。這次學到最好的經驗是：將多個狀態（如賽程進度、休眠狀態、等待佇列）分開維護，並在每個時間點結束後做乾淨的狀態重置，可以讓原本繁瑣混亂的規則變得清晰又好除錯。
